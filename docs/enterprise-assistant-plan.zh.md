# 企业业务助手方案

2026-11-23 更新。本文记录当前 Agent 从源码或 API 接入企业业务的目标流程、已具备的能力与后续验收项。采购入库单是验收案例，其他系统沿用同一流程。

## 整体流程

客户在当前 Agent 的普通聊天里提供源码路径、API 定义或已接入的 API 地址，说明希望办理的业务。例如“@企业业务，把这个项目里的采购入库单功能转成当前 Agent 的技能”。标签标明业务目标，Agent 根据对话判断客户想咨询、盘点、接入还是使用已有功能。

| 阶段 | Agent 的工作 | 客户可见的结果 |
| --- | --- | --- |
| 1. 确定业务范围 | 从页面入口、按钮事件、客户端函数或 API 描述整理候选动作。客户要求“全部”时先列清单，记录每个候选的来源，并标出尚待核实的页面逻辑。 | 当前准备覆盖哪些动作，以及范围的依据。 |
| 2. 查找调用认证 | 查看操作声明的认证方案、登录接口、必填字段、凭据传递方式和登录前的数据依赖。需要实际访问受保护接口时再收集缺失值。 | 沿用已有会话或在私密表单填写所需值。缺少接口定义时，可直接在聊天中补充。 |
| 3. 汇总接口和依赖 | 按动作列出请求顺序，标明字段来自用户、当前会话、上游返回值还是计算规则。按依赖取数并校验类型，唯一匹配自动带入，有歧义才请用户选择。 | 客户按名称、单号等业务信息表达意图，Agent 组装实际请求。 |
| 4. 逐个跟踪接口 | 从入口追到请求、后端校验、返回字段及使用结果的位置。记录默认值、单位换算、金额精度和状态限制的证据。只提供 API 时，把页面规则的证据缺口列出。 | 能说明某个动作走到哪里、已确认哪些规则、还缺什么资料。 |
| 5. 验证业务结果 | 查询核对目标记录和关键字段。写入在获准环境按用户意图验收，取得标识后回查草稿、金额和状态。响应丢失先核对已有结果，再决定是否重试。提交和审核分别确认意图。 | 每项有独立结果。遇到阻塞，说明原因，其他可独立验证的动作继续。 |
| 6. 注册为当前 Agent 的技能 | 将通过验收的能力绑定到当前 Agent，保留版本、证据和回查依据。按用户能办理的动作命名，认证、主档匹配等依赖由执行过程调用。 | 在当前 Agent 的「技能」里找到已注册功能，之后用普通聊天调用。 |

以“按单号查看详情”为例，若详情接口要求内部 ID，先依据源码或契约找到单号查询接口，取得唯一匹配的 ID，再读详情并核对单号。有多个匹配时展示日期、往来单位等能帮助选择的信息。一个业务动作可以组合多个接口，同一个公共查询也可以服务多个动作。

### 进度、恢复和交付顺序

- **清单与进度。** 保存当前账号和 Agent 的候选清单，区分已发现、待验证和已注册，附上证据入口、卡点与下一步。聊天里可以问“发现了哪些动作”“哪些已经能用”“上次卡在哪里”。每次只返回当前范围的一页结果。
- **逐动作追踪和续跑。** 组合查询逐接口保存验收进度，包括接口、参数来源、通过状态和后续步骤需要的字段。服务重启后可以在同一 Agent 的聊天里说“继续验证上次的动作”。系统核对接口定义、连接、样例和权限，从首个缺失或失效的检查点继续。涉及私密登录时还会核对验证会话。
- **完整业务验收。** 先验证查询链，再在获准的测试环境验收写入及回查。比较原客户端和技能在相同输入下的结果。一个动作验收通过即可发布，同一模块其他动作的进度独立记录。

### 当前实现与下一批工作

| 能力 | 当前进展 |
| --- | --- |
| 盘点与查询进度 | 聊天工具 `discover_enterprise_actions` 从指定范围提取源码动作或 API 操作候选，独立保存清单。盘点只读取定义；注册和验收另行执行。`get_enterprise_progress` 支持按清单标识或业务范围查看已发现、待验证和已注册的项，逐页返回证据及阻塞原因。旧注册记录也可查询。 |
| 认证与技能 | 已有认证契约检查、私密表单和登录前依赖查询。已有查询试查、受支持的保存验收及当前 Agent 的技能目录。进度中的“已注册”指该 Agent 的注册记录与当前连接有效；会话中能使用的技能还取决于当前权限。 |
| 组合查询 | Agent 根据客户的业务目标，用 `register_enterprise_action` 将清单中同一已接入服务的多个 GET 定义成一个动作。每步的路径或查询参数可以取自客户输入、前面步骤的返回字段或契约中的常量。列表可以按多个字段筛选，恰好一条才进入下一步，详情可再核对业务标识。整条链验证通过后，当前 Agent 的「技能」显示这个业务动作。 |
| 逐接口检查点 | `get_enterprise_progress` 列出该清单的组合动作。`get_enterprise_action_progress` 按动作查看各接口状态、卡点和下一步。`resume_enterprise_action` 在已有检查点上继续验证。并发恢复同一动作时会串行执行。同一个已发布技能在用户正式办理时始终从头查询最新数据。 |
| 后续验收 | 对照原客户端与目标环境中的真实业务结果，覆盖更复杂的筛选和分页。将包含提交、审核等写操作的组合动作接入现有的确认、回执与回查流程。 |

盘点和整批注册开始时都保存候选清单。查询进度会核对该版本的已完成注册记录与当前连接。源码动作或契约变化后，旧版本的成功记录不能作为新版本的验收依据。代码与契约只提供候选范围，多接口业务动作的验收仍需核对完整调用链。

2026-11-23 在隔离目录用聊天工具对 ERP 项目做了只读盘点。以“采购入库单”为范围，共发现 17 个候选，8 个匹配到客户端源码调用，9 个依据来自 OpenAPI。随后通过进度工具读回相同清单。扫描达到源码发现上限，并报告部分客户端动作暂不支持，因此页面覆盖率仍待逐项核对。本次记录用于验证盘点流程，未访问业务服务或向用户的 Agent 发布技能。

### 采购入库单组合查询验收

聊天示例：“@企业业务，把这个项目里按单号查看采购入库单详情的功能注册为技能。” Agent 从源码盘点中定位列表和详情接口。验收单号可以从已接入服务的查询样例自动取得。若有业务输入无法从样例推导，聊天工具会列出缺少的字段名。本例按以下字段传递数据。

| 步骤 | 请求和业务校验 | 通过后保存 |
| --- | --- | --- |
| 按单号找到单据 | 将客户的单号传给 `GET /purchase/order/page` 的 `billNo`，用 `data.total` 核对本页是否包含全部候选，再在 `data.records` 中核对单号，要求唯一匹配。 | 本步检查点及详情查询所需的 `id`。 |
| 读取并核对详情 | 将上一步的 `id` 传给 `GET /purchase/order/{id}`，核对返回的 `data.order.billNo` 与输入一致。 | 本步检查点及整个动作的注册状态。 |

使用 ERP 项目的实际客户端源码和 OpenAPI 定义，在隔离目录用模拟 HTTP 响应完成了这条链的验收。令详情接口第一次返回 503 后，进度显示 1/2。重新创建服务实例并恢复，列表共调用一次、详情共调用两次，最终技能目录出现“按单号查看采购入库单详情”。真实 ERP 的数据和权限仍需在目标环境验收。

## 聊天里的 `@企业业务`

在当前智能体的聊天框输入 `@`，选择 `@企业业务`，然后像平常一样发送消息、添加附件和追问。标签指明讨论的业务范围。可以问“采购入库单有什么用”，也可以提供源码路径、OpenAPI 定义或已接入的 API 地址，并请智能体注册功能。智能体按对话意图使用工具，消息、工具调用和答复都在同一会话中。

要查看已注册的功能，在聊天页右上角的面板菜单打开「技能」。「企业业务技能」汇总当前智能体历次注册且仍可用的功能，可按业务名称、工具名或操作类型搜索。注册成功后，已打开的面板会自动更新。

客户可以在聊天中提供源码、API 定义或补充登录接口。Agent 可用 `inspect_enterprise_authentication` 查看认证方案、请求字段及响应字段，根据接口或源码中的字段映射组装登录请求。业务查询支持 HTTP Basic、Bearer 和请求头 API Key。对于返回凭据的 JSON 登录 POST，客户在当前聊天的私密认证表单填写所需参数。登录前依赖的 GET 按字段依赖顺序调用，唯一结果自动带入，多个候选显示供客户选择。登录在已接入的服务地址执行，凭据仅在当前账号、Agent 和聊天的内存会话内使用。

## 部署与接入

服务端可通过 `AGENTSCOPE_ENTERPRISE_BUSINESS_CONFIG` 读取一份 JSON 配置，也可以在 `create_app(enterprise_business=...)` 传入 `EnterpriseBusiness`。下面是部署配置示例。

```json
{
  "directory": "/var/lib/agentscope/enterprise-business",
  "source_roots": {
    "erp-owner": ["/srv/checkouts/erp"]
  },
  "api_documents": {
    "erp-owner": {
      "https://erp-test.example.com/openapi.json": "/srv/checkouts/erp/docs/openapi.json"
    }
  },
  "read_apis": {
    "erp-owner": [{
      "document": "/srv/checkouts/erp/docs/openapi.json",
      "base_url": "https://erp-test.example.com/api",
      "token_env": "ERP_TEST_READ_TOKEN",
      "samples": { "/purchase/order/{id}": { "path": { "id": 42 } } }
    }]
  }
}
```

共享部署应由认证中间件把已验证的账号 ID 写入 ASGI scope 的 `agentscope.user_id`，或使用提供稳定 `identity` 的 Starlette 认证用户。受保护账号的业务导入与聊天调用都校验这一身份。仅限单用户本机部署时，可在配置中显式填写 `local_user`，并把服务直接绑定到回环地址。容器部署需将源码挂载给后端并持久化 `directory`。

可选的 `limits` 用于调低导入体积、源码扫描、单批操作数、每页返回量、并发验证数和认证缓存上限。例如 `"limits": {"max_operations": 500, "page_size": 10, "concurrent_probes": 2}`。程序接入可向 `EnterpriseBusiness` 传入 `EnterpriseLimits`。注册和验证回执继续返回原有 `reason`，失败时也可返回 `diagnostic`，包含原因码、阶段及可用的步骤和 HTTP 状态。诊断日志和回执只保留这些元数据。

服务在进程内复用已解析的契约、只读工具绑定和保存验收文件哈希。收到新请求时，会检查文件及目录的状态和当前连接授权，必要时重新加载。源码盘点会记录扫描和导入解析依赖的文件与目录，重跑时仍检查依赖变化。含登录或保存确认的调用按当前会话处理。

查询样例以 OpenAPI 路径为键。只提供源码时，平台会按请求方法和路径查找已授权的接口契约。唯一匹配的客户端动作使用同一份源码执行计划进行试查和注册。使用业务响应包裹层的 API 可指定 `"success": {"field": "code", "equals": 200}`。源码参数经过复杂变换时，可在对应路径的样例中直接提供客户端动作的输入参数。

静态凭据通过 `token_env` 配置。查询使用 OpenAPI 的 Bearer 或请求头 API Key 方案时，服务按对应方案发送凭据。提供交互式登录定义时，认证由会话里的私密登录表单处理。

已有保存验收适配器的服务，在创建 `EnterpriseBusiness` 时通过 `save_registries={"erp-owner": [registry]}` 传入为该账号授权的 `SaveBusinessRegistry` 实例。匹配的 POST 操作会返回验收工具和目标。可以在对话中请当前 Agent 发起验收，并按原有确认流程核对写入与回查结果。验收服务、契约或源码版本变化时，转换结果会包含待处理原因。

## 员工怎样从客户端转到聊天

员工在官方聊天中说“查最近 30 天的单据”或“按这两行明细开一张单”。助手找到当前企业发布的业务，列出结果或建立草稿。员工可以直接说“把第二行的单价改成 6 元”，检查更新后的明细，确认后拿到业务系统生成的单号。已有客户端继续提供业务规则和验收对照，按已验证的任务逐项迁移。

## 客户端与 API 怎样变成工具

| 接入步骤 | 交付物与通过条件 |
| --- | --- |
| 还原一个用户任务 | 沿客户端的查询、编辑或保存入口追到实际 API，记录字段来源、默认值、单位、主档选择、联动、计算顺序、精度、校验和错误处理。标注客户端版本及规则对应的文件、函数。 |
| 对照 API | 用接口定义和批准使用的请求、响应样例核对读写依赖、权限、请求体、返回标识与按业务编号回查的路径。历史接口与当前客户端实际调用冲突时，以复现结果核实。 |
| 编写可执行的业务定义 | 为每个操作声明用途、适用企业、输入输出、读写副作用、依赖、登录要求、校验规则与成功判据。模型可协助起草。金额、单位换算和字段映射交给服务端确定性规则执行。证据不足的规则列为待核实，相关操作暂缓开放。 |
| 验证和发布 | 在同组输入下比较客户端和助手的草稿、请求以及回查结果，记录业务定义版本和差异。发布回执提供“添加到当前聊天并试查”的一次操作，服务端刷新该会话的工具目录后发起只读试查；回执分别标明发布版本、实际执行的操作和结果。 |

## 企业如何接入一项已有业务

接入人员在当前 Agent 中提供可读取的源码或 API 定义，说明业务范围。以“新增采购入库单”为例，Agent 沿保存入口或接口定义追踪规则，进入写入验收时再使用测试环境中获准的样例。平台先产出可复核的业务定义草稿。员工聊天只使用该企业已发布的版本。

| 接入位置 | 输入与处理 | 交给下一步的结果 |
| --- | --- | --- |
| 接入工作区 · 源码 | 首个业务可用 Agent 的读码工具定位页面事件、计算和保存函数。需要批量提取时，可选用 CodeToSpec CLI 生成 `graph.json`，导入其中的候选规则和源码引用。对 Vue 单文件组件单独核对脚本、模板触发点及被调用函数。[CodeToSpec](https://github.com/edouard-claude/codetospec) | 业务动作、字段含义、触发条件、公式、舍入时点及其对应的源码版本和位置。 |
| 接入工作区 · 接口 | 优先导入企业维护的 OpenAPI。需要核对实际请求时，可选用 `mtbun/api-anything` 分析企业测试环境的 HAR，并生成候选 OpenAPI。仅导入当前业务所需、已脱敏的操作及样例，录制账号的凭据留在测试环境。[api-anything](https://github.com/mtbun/api-anything) | 操作标识、请求字段、响应标识和调用顺序，以及哪些字段须由客户端算好再提交。 |
| 企业工具服务 · 验证与发布 | 按同一个用户动作关联源码规则与 API。系统有权威试算接口时优先调用；客户端独有的计算进入可测试的服务端规则。用能区分两种算法的输入比较原客户端预览、候选规则输出和保存请求，再做测试账套回查。 | 版本化业务定义，含工具说明、输入输出、读写权限、执行规则、接口映射、验证样例及回查条件。发现不一致时保留草稿和差异，修正后再发布。 |

### 可选的独立企业工具服务

部署希望复用已有 Java 服务时，可以在服务前提供 MCP 接口，将 [Agent Service](../examples/agent_service/main.py) 的 HTTP MCP 客户端接到该地址。Java 已有目录、运行和回执 REST 接口，可以复用。下表是拟增加的 MCP 工具名称。服务端从可信的会话身份确定企业和用户，并逐次检查权限。

| 员工动作 | 拟提供的工具 | 服务端行为 |
| --- | --- | --- |
| “我能办哪些业务？” | `business_search`、`business_describe` | 按当前企业和员工可见范围读取发布目录，返回用途、版本、参数和样例。复用现有目录接口 `GET /agent/directory/skills`，在服务端做范围过滤。 |
| “查最近 30 天的单据” | `business_query` | 调用已发布业务的读取操作。可复用 `POST /agent/businesses/published/{enterprise}/{slug}/run`；调用类型取决于操作定义的副作用。 |
| “建两行，第二行改单价” | `draft_create`、`draft_update`、`draft_preview` | 按业务定义解析字段，按稳定行标识修改，执行当前版本的规则，返回新修订号、逐行金额和合计。 |
| “确认保存，再查这张单” | `draft_submit`、`document_lookup` | 保存前绑定身份、授权和最新修订的确认。成功后按单号重读业务系统；已保存但回查失败时只重试查询。现有 `GET /agent/businesses/runs/{id}` 可追踪平台运行回执，业务实查以目标系统返回的单据为凭。 |

采用独立 MCP 服务时，可以用稳定的工具名称，每次发现业务时读取企业目录。官方工作区管理器将默认 MCP 配置用于新工作区，因此首次接入要为已有工作区也配置该服务，并验证原聊天可用。此后新发布业务只更新目录。首轮联调先在既有聊天中发现一项业务并完成只读查询，再验证两行草稿、授权续办、确认及按单号回查。[工作区实现](../src/agentscope/app/workspace_manager/_local_workspace_manager.py)

## 三个组件各负责什么

| 组件 | 职责 |
| --- | --- |
| 官方聊天前端 | 展示对话、工具进度、草稿摘要、确认请求和回执。首版用聊天消息及原生确认交互完成两行编辑，企业人员和单据字段配置留在服务端。 |

工具目录要能回答“我能办什么、需要提供什么、下一步是什么”。按业务提供查询、查找主档、创建或修改草稿、预览、提交、按单号回查等能力。每个工具公开名称、用途、参数与结果示例、常见失败原因和恢复动作。发布或升级后，已有聊天重新读取可用版本。员工无需了解仓库路径、内部 ID 或逐个安装依赖工具。

## 制单、授权和保存

1. **录入草稿。** 在服务端以业务身份、目标数据范围和草稿 ID 隔离存储。数据范围由目标系统定义。草稿记录业务定义版本、修订号、表头及带稳定标识的明细行。每次修改都校验字段、重算受影响的金额并递增修订号。重载聊天后可继续编辑。
2. **按操作申请权限。** 查询主档使用读取权限，写授权推迟到员工要求保存时。登录失效时发起重新认证，登录成功后按原身份恢复同一草稿。已登录但权限不足时，说明缺少的具体操作和授权入口；获得授权后重检。身份适配器声明登录方式，按业务系统要求使用账号、单点登录跳转或多因素验证；凭据在对应的认证页面输入。取消或拒绝都保留草稿。登录或授权完成后先展示待确认的草稿。
3. **确认指定版本。** 保存前展示目标数据范围、操作、表头、明细和合计。确认绑定用户、草稿修订号和本次请求内容。任何后续编辑都需要确认新版本。服务端在提交前再次核验权限及版本。
4. **提交与回查。** 服务端记录本次提交标识，并在上游支持时传入幂等键。双击或重连读取同一提交结果。若保存响应丢失，先按上游可检索的关联标识核对；缺少可靠回查条件时保留“结果待核对”，交由人工核实。取得单号后读取详情，对照确认的草稿，再报告实查结果。

## 首次验收：采购入库单

在本次获准的本地 ERP 测试账套中，用原客户端和助手录入相同的表头、两种货品及单位。账套由该系统的登录上下文确定。原客户端用于预览对照，真实保存只由助手执行一次。此场景验证通用制单流程，采购专属公式归入该业务定义。

采购客户端的 `PurchaseOrderView.vue` 在 `calcDetailRow` 中按“应收片 × 厂价片 + 装车费”计算行应付，并按结算精度舍入。业务系统的 `PurchaseOrderController.syncFactoryAmountFields` 汇总请求中的行应付，缺值按零计。验收应把应收片和入库片设为不同值，才能发现误用入库数量的实现。

| 步骤 | 可观察的通过条件 |
| --- | --- |
| 发布后试查 | 在发布所在聊天发起最近 30 个自然日（含当天）的只读查询，记录账套、日期范围和实际回执。返回零条时记录空结果；遇到鉴权失败则进入对应的登录或授权流程。 |
| 录入和改第二行 | 样例 A 为应收 10 片、入库 9 片、厂价每片 3 元、装车费 2 元，行应付 32 元。样例 B 为应收 4 片、入库 3 片、厂价每片 5 元、装车费 1 元，行应付 21 元。把 B 的厂价改为 6 元后，只更新第二行，行应付 25 元，货品应付合计从 53 元变为 57 元。 |
| 授权后恢复 | 在保存时触发授权，刷新或重新进入聊天。授权成功后仍是同一草稿，两行数量、最新单价和合计均与授权前一致。此时业务系统新增记录数为零。 |
| 确认和重试 | 只有确认最新修订才提交。重复点击或模拟响应丢失后，同一提交最多生成一张单；界面可区分保存中、已保存、结果待核对。 |
| 按单号查回 | 使用保存返回的业务单号查询，核对账套、供应商、仓库、两种货品、应收与入库数量、行应付 32 元和 25 元及货品应付合计 57 元。保留脱敏后的单号、草稿版本、运行编号和对照结果。 |

首张单通过后，再选一种字段及计算口径不同的单据，例如销售出库单。复用同一组聊天交互、草稿、授权、确认与回查工具，仅替换业务定义和目标系统映射。若第二种单据需要在前端或通用运行器里新增按单据名称判断的分支，就回到工具设计，补齐缺少的通用能力。
